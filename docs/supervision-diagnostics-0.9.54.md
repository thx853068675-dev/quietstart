# 0.9.54-test：退出归因与监督恢复验证

这是从 v0.9.52 建立的独立验证分支，未包含其他分支正在开发的识别改动。

## 修改

- `recoveryReason` 保存监督检测到的问题；`plannedAction` 保存应用计划动作。兼容字段
  `expectedAction` 不再由计划动作覆盖恢复原因。
- `recoveryAttemptKnown` 区分确实传入了第 0 次和本次启动根本没有恢复次数参数。
- 监督主动终止前保存 token、PID、命令时间；命令成功后标记 completed。只有系统退出详情
  的 PID、时间与同一 token 的已完成命令匹配，才设置 `selfStopVerified`。
- 没有有效 PID/退出时间时不推断为监督主动终止。普通 `activation` / `worker-restart`
  标签不能覆盖系统的用户终止请求。主动结束连接和应用升级仍停止恢复。
- 系统只返回 `User Request` 时，界面显示“系统报告终止请求”，不再直接写“用户结束应用”。
- 导出格式升级为 `schemaVersion: 2`，包含 `exits` 与 `supervisorTimeline`。退出记录最多
  20 条，监督时间线最多 120 条。记录状态变化和命令结果，不对每次轮询追加一条日志。
- 时间线包括监督 PID、工作 PID、与工作 PID 对应的 UiTest PID、心跳/RPC、恢复原因、命令及
  返回码。命令返回成功不等于恢复完成，实际恢复仍以新工作进程与新鲜 RPC 为准。

## 离线验证

- 连接与退出诊断 32 项 Node 测试通过，其中退出诊断与传输、故障钩子为 13 项。
- 本轮完整 Node 回归 586 项中，322 项先通过；264 项工作模块用例因测试加载器尚未注册
  两个新增依赖失败。补齐测试加载器后，工作模块与诊断两组共 277 项全部通过。
  合计 586 项不同用例通过（没有把重复运行计入数量）。
- 真实生产 shell 状态机在虚拟时钟和 OS 命令替身下的 7 项测试通过：进程退出、RPC 停滞、
  灭屏暂停、主动停止、锁互斥、三次上限，以及完整命令时间线。
- 主包与内嵌工作模块构建成功，版本 `0.9.54-test` / 95400，通过单交付包验包。

这些结果不是实机恢复成功的证明。

## 真机压力测试

先安装此版本，并在手机完成本机连接。保持解锁、连接 USB，并暂时不要手动操作手机。

```sh
python3 scripts/stress-supervision.py --serial 设备序列号 --case observe --out /绝对路径/observe.json
python3 scripts/stress-supervision.py --serial 设备序列号 --case kill-worker --out /绝对路径/kill.json
python3 scripts/stress-supervision.py --serial 设备序列号 --case stall-rpc --out /绝对路径/stall.json
python3 scripts/stress-supervision.py --serial 设备序列号 --case end-session --out /绝对路径/stop.json
```

脚本只接受此测试版本，核对当前进程与会话，并确认故障请求确实被应用接收。
此 6.1 系统拒绝 shell 对应用发 kill / STOP 信号，故使用测试版内部钩子：
`kill-worker` 调用进程自身的 exit(77)；`stall-rpc` 暂停识别 await 70 秒，心跳仍运行。
这分别模拟进程消失和 RPC 停滞，不代表实际冻结整个 OS 进程。
钩子仅允许 `0.9.54-test`、当前会话 token、10 秒内的单次请求；正式版本不会启用。
每个故障观察最长 110 秒，正常后台与主动停止观察各 45 秒。不会耗尽内存或忙循环，
不修改系统后台策略，不删除用户规则。

`end-session` 会点击应用自身的“结束本次连接”，完成后需重新本机连接。
超过三次恢复预算前也应开始新会话，避免把额度耗尽当作一次独立故障的失败。

输出主文件包含采样时间线；相邻 `.journal.jsonl` 和 `.exits.json` 保存本轮诊断。
进程注入用例证明故障恢复和停止行为，不能证明真实厂商后台杀进程的原因相同，也不能
替代数小时后台运行、锁屏或拔线验证。

## 6.1 真机签名与安装

设备 HBN-AL00 / OpenHarmony-6.1.1.120 / API 24。
使用小白现有华为登录、现有证书与私钥，为此手机创建轻启专用调试 Profile，再通过
小白内置 native signer 和整合版 `signQuietStart` 对内外 HAP 重签。未重置或撤销证书。
此次签名没有调用 DevEco / SDK 签名工具；构建仍使用项目现有 SDK。

单个主 HAP 安装成功，首次连接从手机自动安装工作模块、允许本机调试身份，界面显示在线。
最终测试包 SHA-256：`25b8693e4ff7e07e4a80e12d00af20600fa97ed50ce5c7f3dce4be05f806f7d7`。

实机发现此系统下 shell 直接重定向读取 `/proc/PID/cmdline` 不可用，而 `cat` 可以读取。
已修正监督时间线的 UiTest PID 采集和压力脚本的目标 PID 校验，避免采集失败被误判为进程消失。
修正后生产 shell 的 7 项回归通过，主包重新构建、重签、安装。

日志由监督进程写入 `/data/local/tmp/quietstart-supervisor`；恢复时以当前 token 绑定的
Want 参数传递最近记录和主动停止凭据。工作模块通过已有 TestKit 调试通道每分钟读取一次，
由应用自身写入私有目录；灭屏期间不主动同步，相同快照不重复写盘。导出只使用本地已同步数据。

此设备 shell 的整数乘法会将毫秒时间戳溢出为负数，已改为格式拼接；UiTest 命令行包含
NUL 分隔符，使用 `grep -zF` 匹配进程 token。主机测试不能覆盖这些系统工具差异。

### 已完成结果（USB 连接）

- 首次单包安装、本机自动安装工作模块及激活成功；签名完全使用小白材料和工具。
- RPC 停滞：同一工作 PID 心跳继续更新，RPC 停在旧时间；监督识别 `rpc-stalled`，
  第一次恢复后得到新工作 PID 和新鲜 RPC。自最后一次 RPC 到恢复约 50 秒。
- 此次系统对监督 force-stop 仅返回 reason=2、空 message、PID=-1、timestamp=0。
  因此 `selfStopVerified=false`，保持“未获得系统佐证”；没有伪造退出细节或推断为用户清理。
  监督命令时间线仍保留 force-stop 返回码、工作 PID、恢复原因及后续新会话信息。

- 进程退出：测试版自退出码 77，旧 PID 55576 消失；同一监督 PID 54991 检测
  `process-exited` 并按第二次恢复的退避启动新 PID 56109，约 34 秒恢复新鲜 RPC。
  系统返回了旧 PID、退出码 77、退出时间，均原样保留。
- 主动结束：点击应用自身“结束本次连接”，控制状态变为 stopped，工作进程退出；
  连续观察 45 秒未被监督再次启动。
- 普通后台观察：45 秒内工作 PID 保持不变，心跳和 RPC 持续刷新，无恢复重启。
- 最后仅增加了重复快照不写盘、主动结束提示文案修正；13 项诊断回归再次通过，
  重新构建并使用相同小白签名流程安装。

本轮没有拔线、数小时待机、锁屏后系统回收、整组进程被系统同时结束等验证。
这些测试证明本机监督能应对上述两类注入故障，不能据此承诺后台永久常驻，
也不能证明用户原始日志中的退出一定由相同原因造成。
