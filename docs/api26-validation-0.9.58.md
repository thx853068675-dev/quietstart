# API 26 真机验证：0.9.58-test

2026-09-16，Pura X（VDE-AL10），OpenHarmony 7.0.0.105 / API 26。USB 保持连接；测试期间临时延长自动熄屏，结束恢复原配置。没有做长时间能耗或拔线验证。

## 方法

先用设备原有 0.9.52 跑 10 个应用各一次，再覆盖安装优化测试包；原有 29 条规则保留。应用按真实主模块/入口冷启动，不杀轻启。逐轮读取运行记录、心跳、RPC 和监督状态。广告内容与出现频率可能不同，因此这些是现场观察样本，不是同一广告的严格随机 A/B 实验。

测试涵盖大麦、QQ 音乐、虎牙、下厨房、斗鱼、爱奇艺、芒果 TV、喜马拉雅、智行火车票、驾校一点通；新版本另加入此前无规则的 12306、携程。

## 真机发现并修复的兼容性问题

初版复用布局时，将 API 24 的读取后复核 150 ms 限制也套给 API 26。大麦一次读取 294 ms、读取后复核 207 ms、总计 501 ms，本来处于 API 26 的有效时限内，却被丢弃并等待下一帧。

现在 API 26 保持读取 700 ms、读取后复核 300 ms、总计 800 ms；API 24 仍使用自己的时限。没有取消时效、前台、窗口、规则启用和遮挡校验。增加 207 ms 可通过、310 ms 必须拒绝的回归用例。最终包真机大麦复核 201 ms 正常点击。

API 26 继续使用 Driver.dumpLayout，复用当前完整布局后不再为已确认按钮额外读取一遍。API 24 的命令行获取和新样式两帧复用没有移植到 API 26。

## 验证结果

- 旧版基线：10 次启动全部到达目标，8 次点击，逐轮记录中 7 次消失确认。
- 初版试跑：完成 13 次采样后主动停止，修复 150 ms 限制问题；不混入最终包统计。
- 最终包：12 个应用、24 次启动全部到达目标；16 次点击，逐轮记录中 15 次消失确认（最后一次的确认随后才写入），新增 12306、携程两条规则。第二轮这两条均进入已有规则的新快照路径。
- 最终循环只有一个工作 PID，监督恢复次数 0；未见循环期间新增退出或会话异常。结束时电池温度 39°C。
- 31 条规则包含原来的全部 29 条。内置工作模块与设备安装摘要一致。

成功点击样本的“匹配＋复核”耗时：

| 应用 | 旧版一次样本 | 最终版样本中位数 |
| --- | ---: | ---: |
| QQ 音乐 | 360 ms | 93 ms（2 次） |
| 虎牙 | 464 ms | 92.5 ms（2 次） |
| 喜马拉雅 | 664 ms | 234 ms（1 次） |
| 智行火车票 | 1231 ms | 491 ms（1 次） |
| 大麦 | 435 ms | 508 ms（2 次） |
| 爱奇艺 | 237 ms | 309 ms（2 次） |

不是所有应用样本都更快。最终 14 次已有规则成功点击样本的中位数为 270.5 ms，旧版 8 次样本为 564 ms；两组组成和广告内容不同，不能把这个差值宣称为普遍提速比例。

长尾仍存在：喜马拉雅曾因复核 304 ms 超过 300 ms 被拒绝后重试；智行出现读取 826 ms、总计 820 ms 的超时；携程也有读取 715 ms、总计 805 ms 的超时，后续在有效新帧中完成点击。没有为了提高命中次数放宽原来的 API 26 时限。

没有逐帧录像确认每一次启动都出现广告，也没有人工逐项审核全部点击，因此 16/24 不能作为广告识别成功率。未匹配轮次不等于没有广告。这次不能证明所有广告都在一秒内完成点击。

耗时“匹配＋复核”来自工作模块运行记录，不包含等待广告出现；“发现前台至点击”也不等于广告画面出现至点击，不能据此承诺所有广告一秒内关闭。

539 项离线回归全部通过，内外包构建通过。详细原始记录仅保存在本地忽略目录，避免公开用户手机画面与应用内容。
